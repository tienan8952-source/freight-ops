# /健康檢查

依序檢查並整理成一份摘要：

1. **Supabase 連線**：呼叫 `GET /rest/v1/vehicles?select=id&limit=1`
   （用 anon key 即可），確認回應正常（非 401/500/逾時）。

2. **各表筆數（與上次檢查比較）**：對 `scripts/backup.ps1` 裡 `$Tables`
   列出的每張表查 `select=count`（或直接數陣列長度）。跟上次檢查結果
   比較筆數變化：
   - 讀 `backups/.health-check-last.json`（如果存在）當作上次結果
   - 這次查完之後，把這次的結果覆寫回 `backups/.health-check-last.json`
     （這個檔案在 `backups/` 底下，已經被 `.gitignore` 排除，不會進 git，
     純粹是本機這次跟下次比較用）
   - 摘要裡列出「哪幾張表筆數有變化、變化多少」，第一次執行沒有上次
     結果可比較就直接列目前筆數，註明「首次執行，無比較基準」

3. **資料庫容量、Storage 容量、距離免費額度上限多少**：這些是 Supabase
   帳號/專案層級資訊，REST API（anon/service_role key）查不到，需要
   Supabase 的 Management API 個人存取權杖或人工到後台看。摘要裡直接
   標「未驗證，請至 Supabase 後台 Project Settings / Usage 頁面確認」，
   不要用查得到的東西去猜容量。

4. **最後備份時間**：讀 `backups/` 底下最新（依資料夾名稱 `yyyy-MM-dd`
   排序）一份的 `manifest.json`，取 `exported_at`。距今超過 7 天要在
   摘要裡標記提醒（跟系統前端「系統維護」頁、總覽頁的提醒邏輯是同一個
   7 天門檻，但這裡看的是 `scripts/backup.ps1` 產生的伺服器端備份，不是
   瀏覽器 `localStorage` 記錄的前端備份，兩者是獨立的，都要提一下現況）。

5. **最後一次 Supabase 活動時間（七天無活動會被暫停）**：沒有直接的 API
   可以查「Supabase 認定的最後活動時間」，只能用「這次健康檢查本身能
   成功打 API」這件事當作「現在還是活著」的證據；沒辦法回答「上次真正
   有活動是幾天前」，摘要裡標「未驗證，Supabase 有沒有被判定為閒置只能
   到後台看專案狀態是否顯示 Paused」。

6. **未處理的 agent_alerts**：
   `GET /rest/v1/agent_alerts?level=eq.action&resolved_at=is.null`
   （需要 service_role key），列出筆數與標題。

7. **未提交的 git 變更**：`git status`，列出有沒有未 commit 的檔案。

8. **各文件的「最後更新」日期**：對 `docs/` 底下（含 `docs/tools/`、
   `docs/tasks/`）每份 `.md` 檔案查 `git log -1 --format=%ad --date=short -- <檔案>`，
   列出超過 30 天沒更新的檔案清單（這個專案目前每份文件都是同一天
   建的，之後隨時間拉長才會真的篩出東西，第一次執行大概率是空清單，
   這是正常的，不用因為清單是空的就懷疑指令寫錯）。

9. 整理成一份簡短摘要回報給使用者，異常項目（連線失敗、超過 7 天沒
   備份、有未處理的 action alert、有未提交變更、有超過 30 天沒更新的
   文件）要特別標出來。

## 禁止事項
- 不要因為健康檢查發現異常就自己動手修（例如發現未處理的 alert 就自己
  標記已處理，或發現久未更新的文件就自己動手改）——健康檢查只回報
  現況，處理動作交給使用者決定或另外用對應的指令處理。
- 不要為了「查資料庫容量」去猜測或估算數字充數，查不到就老實標
  「未驗證」。
