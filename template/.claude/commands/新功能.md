# /新功能

依序執行，每一步做完才進下一步：

1. **確認範圍**：把要做的功能講清楚到「改哪幾個檔案、影響哪個模組」的
   程度。範圍不清楚就先跟使用者確認，不要自己腦補範圍。
2. **檢查是否影響 RLS**：這個功能會不會新增資料表、新增欄位、或改變
   誰可以看/改哪些資料？會的話，先想清楚 RLS 政策要怎麼寫（參考
   `supabase/schema-v2.sql`、`schema-v3.sql` 既有的 `is_admin()`/
   `is_active()`/`has_perm()` 寫法），並印出完整 SQL 給使用者到 Supabase
   SQL Editor 執行（不要自己用 service_role key 直接改 schema）。
3. **改 schema（若需要）**：等使用者回報 SQL 已執行成功再繼續下一步。
4. **改前端**：`js/core.js` 的 `M` 物件、對應的 `js/*.js` 檔案。新模組
   要記得同時補：選單（`NAV_GROUPS`/`MODLIST`）、權限鍵（`PERM_OF`）、
   CSV 匯出（`m.cols`／`exportCSV()` 通用邏輯自動涵蓋）、匯入對應
   （`IMPORTABLE` 陣列，見 `js/importer.js`）。
5. **驗證**：本機起靜態伺服器 + Playwright 灌假登入，實際點過這個新
   功能，確認沒有把其他畫面弄壞（可比照 `docs/tools/node-npm.md` 的
   驗證方式）。
6. **commit**：訊息說明做了什麼、為什麼。
7. **push**。
8. **回報**：一行說明做了什麼、改了哪些檔案。

## 禁止事項
- 不要一次做兩個以上的功能。
- 不要在做這個功能的同時「順便」重構其他不相關的程式碼。
- 不要跳過 RLS 影響評估，即使覺得「應該還好」。
