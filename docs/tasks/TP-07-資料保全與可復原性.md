## 階段二｜備份自動化

1. `scripts/backup.ps1`：讀 `.env`，用 service_role key 匯出所有資料表為 JSON，存到 `backups/YYYY-MM-DD/`，每張表一個檔。同時產生 `backups/YYYY-MM-DD/manifest.json`：各表筆數、Storage 檔案數、匯出時間、schema 版本。自動保留最近 12 份，更舊的刪除。`backups/` 加進 `.gitignore`（資料不進 git）。
2. `scripts/backup-storage.ps1`：下載 Storage 裡所有檔案到 `backups/storage/`。大檔案分批，可中斷續跑。
3. 前端「系統維護」頁加：顯示最後備份時間與距今天數；超過 7 天在總覽頁顯示紅色提醒；「下載完整備份」按鈕（JSON + CSV zip）。

## 階段三｜設定備份（不含金鑰值）

`docs/config-snapshot.md`，記錄所有可重建的設定：
- Supabase：專案 ID、區域、方案、已啟用功能、Auth 設定（Site URL、Redirect URLs、Email 驗證開關）、Storage bucket 名稱與政策、所有 RLS 政策清單
- GitHub：repo 名稱、可見性、Pages 設定（分支、目錄）
- 本機：需要的執行原則、PATH、Node 版本

同時產生 `supabase/full-schema.sql`：從目前資料庫狀態匯出完整 schema（表、欄位、索引、RLS 政策、觸發器、function），可在空專案一次重建。

這階段順便處理 `pending-info.md` 裡的兩題：Supabase 實際方案、區域、用量、是否有自動備份，以及 GitHub repo 是否要用 PR 流程、是否開 Dependabot 或 secret scanning——把查得到的事實寫進 `config-snapshot.md`，需要使用者決定的維持在 `pending-info.md` 待回答，不要自己替使用者決定。

## 階段四｜復原手冊

`docs/recovery.md`，四種情境各一套完整步驟，每步附可直接複製的指令：

1. **電腦壞了／換新電腦**：從 git clone 到能繼續開發的完整流程
2. **Supabase 專案沒了／被暫停**：建新專案 → 跑 `full-schema.sql` → 還原 JSON 備份 → 還原 Storage → 改前端的 URL 與 key → 驗證
3. **資料被誤刪**：從最近備份還原單一資料表、不影響其他表的做法
4. **Claude 帳號換了**：重貼專案指示（從 `project-brief.md`）、重跑 claude 授權、確認 `CLAUDE.md` 與 commands 仍在

每套最後要有「怎麼確認真的復原成功」的驗證步驟。

## 階段五｜復原演練

實際做一次，證明手冊可行：
1. 跑 `backup.ps1` 產生一份備份
2. 在 Supabase 建一張測試表，塞幾筆資料
3. 刪掉它
4. 照 `docs/recovery.md` 的步驟從備份還原
5. 驗證資料一致
6. 把演練結果寫進 `docs/recovery.md` 的「已驗證」欄位，註明演練日期與發現的問題
7. 清掉測試表

沒驗證過的手冊等於沒有，這階段不能跳過。

## 階段六｜定期檢查

`.claude/commands/健康檢查.md` 擴充為：Supabase 連線狀態、各表筆數（與上次檢查比較）、資料庫容量、Storage 容量、距離免費額度上限多少、最後備份時間、最後一次 Supabase 活動時間（七天無活動會被暫停）、未處理的 agent_alerts、git 未提交的變更、各文件的「最後更新」日期（超過 30 天未更新的列出來）。

`docs/maintenance.md` — 維護節奏：每週該做什麼、每月該做什麼、每季該做什麼，寫成可勾選的清單。

## 階段七｜驗證與回報

1. 跑一次 `backup.ps1` 確認產出正確
