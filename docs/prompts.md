# 提示詞範本

記錄「這樣講 Claude Code 才做得對」的經驗。每則：情境、建議講法、為什麼
有效、反例。

## 怎麼寫大型任務包

**情境**：一次要做的事情很多、橫跨多個檔案或多個階段。

**建議講法**：分階段寫（階段 A、B、C…），每個階段內容具體到「改哪個檔案、
新增什麼、驗證什麼」；把所有要跑的 SQL 集中列在同一個段落，不要散落在
各階段敘述裡；一開始就講清楚「執行原則」（要不要中途問、什麼情況才停下、
多久 commit 一次）。

**為什麼有效**：分階段讓 Claude Code 可以按順序推進並在每階段做完就
commit，即使中途被打斷或需要恢復，也能從乾淨的階段邊界繼續；SQL 集中
列出方便使用者一次複製貼上到 Supabase SQL Editor 執行，不用在長篇回覆
裡東翻西找；先講執行原則能避免它每改一步就停下來問，浪費雙方時間。

**反例**：把所有需求寫成一段不分階段的長文字，中間夾雜「另外它應該要…」
「對了還要…」的補充，容易讓部分需求被漏掉，也很難分批驗證跟 commit。

## 怎麼描述介面需求

**情境**：想要改視覺設計，但難以用文字精準描述「好看」的標準。

**建議講法**：給具體的數值與參照物，而不是形容詞——例如直接給色票
（`--pri:#2563EB`）、圓角像素數（`--r-card:13px`）、陰影的 CSS 值，而不是
說「要現代一點」「要柔和一點」；描述元件時用結構化的條列（側欄多寬、
Logo 怎麼排、KPI 卡裡面由左到右放什麼），而不是一段話帶過。

**為什麼有效**：Claude Code 對「柔和」「現代」這類形容詞的理解跟使用者
心裡的畫面不一定一致，容易做出「技術上合理但不是你要的」設計；給精確的
token 值跟結構化描述，等於直接把「驗收標準」寫進需求裡，減少來回修改
的次數。

**反例**：「幫我把介面弄得更好看、更專業一點」——這種需求會讓 Claude
Code 自由發揮，結果可能跟預期差很多，還得再花一輪對焦到底哪裡不滿意。

## 怎麼要它停下來

**情境**：任務中有些步驟必須由使用者親自動手（貼金鑰、執行 SQL、互動式
登入），不能讓 Claude Code 自己做。

**建議講法**：明講「只有 X、Y 兩種情況才停下來問我，其他狀況都自己判斷
繼續」，並指定停下前要做什麼（例如「停之前先呼叫 notify.ps1 通知我」）。

**為什麼有效**：把「該停下來的條件」限定清楚，比籠統說「有問題就問我」
更能讓它在大部分情況下自主往前推進，同時保留人工介入的安全閥在真正
需要的地方（金鑰、SQL 這類一旦做錯很難回復或有安全疑慮的操作）。

**反例**：完全不講停下的條件，會讓它預設在很多小地方都自己做決定；或是
講得太寬鬆（「不確定就問我」），容易變成每一步都停下來問，失去自動化
的意義。

## 怎麼避免它一次改太多

**情境**：擔心一個任務包順帶「重構」「順手優化」到不相關的程式碼。

**建議講法**：在任務原則裡明講「只改視覺，不動任何業務邏輯」「一次只做
一件事，不順手改別的」，並且明確列出範圍內/範圍外的檔案或功能。

**為什麼有效**：把範圍邊界寫死，讓它在猶豫「要不要順便修一下這裡」時
有明確的依據拒絕自己的衝動；也讓事後 code review／驗證更容易聚焦在
「這次改動有沒有踩到不該碰的東西」。

**反例**：只講「幫我改個介面」，沒講範圍限制，可能連帶把資料驗證邏輯、
權限判斷都一起「順手調整」了，增加不必要的風險。

## 怎麼要求它誠實回報沒做完的部分

**情境**：任務很大，實際執行完不一定每個角落都做到位，需要它老實說。

**建議講法**：在任務結尾明講「回報有什麼你覺得有疑慮或沒做完的」「文件
不確定的地方要標『未驗證』，不要憑空寫」，給它一個明確、安全的方式承認
不確定，而不是暗示「必須全部做完美」。

**為什麼有效**：如果只問「做完了嗎」，容易得到「做完了」這種不夠精確的
答案；明確給「未驗證」這種輸出格式，等於告訴它「講不確定是被允許、甚至
被期待的」，能得到更誠實、更有用的落差清單。

**反例**：只在最後問一句「都改好了嗎？」，容易得到籠統的「是」而不是
具體哪裡有疑慮。
