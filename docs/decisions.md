# 決策紀錄

格式：日期、決定、理由、當時的其他選項、什麼情況該重新檢討。

**2026-09-16｜為什麼用 Supabase 當後端**
決定：整個系統用 Supabase（Postgres + Auth + Storage + REST API），前端
直接呼叫，不另外寫伺服器。
理由：單人／小團隊要快速做出一個能用的內部系統，Supabase 的 RLS 可以把
「誰能看什麼資料」的規則放在資料庫層，前端不用自己寫一套授權伺服器；
免費方案足夠現階段用量。
其他選項：自架 Node/Express + Postgres（維運成本高，需要自己顧伺服器）；
Firebase（NoSQL，跟現有的「像 Excel 表格」的資料形狀比較不合）。
什麼情況該重新檢討：使用人數大幅增加、需要更複雜的伺服器端商業邏輯
（見「為什麼暫不用 n8n」）、或免費方案的限制（暫停/額度）開始造成實際
困擾時。

**2026-09-16｜為什麼 repo 維持 public**
決定：`tienan8952-source/freight-ops` 維持 public，不改 private。
理由：GitHub Free 方案的 Pages 只支援 public repo；改 private 會直接讓
線上網站失效。原始碼公開的風險（沒有商業機密邏輯、金鑰都已排除在
`.gitignore` 外）低於失去免費 Pages 託管的代價。
其他選項：升級付費方案取得 private repo + Pages（增加固定成本）；改用
其他靜態託管服務（例如 Netlify/Vercel）讓 repo 可以維持 private（需要
額外設定一個新的部署管道）。
什麼情況該重新檢討：原始碼裡開始出現不適合公開的商業邏輯，或有能接受
的付費預算時。

**2026-09-16｜為什麼照片放 Supabase Storage 而不是資料庫欄位**
決定：照片改存 Storage bucket `scans`，資料表欄位只存路徑字串。
理由：一開始直接把照片轉 base64 存進資料表欄位，很快就讓資料庫容量
逼近免費額度上限；Storage 有獨立的容量配額且是為檔案設計的。
其他選項：外部圖床（多一個依賴、金鑰管理更複雜）；持續用 base64（會
持續逼近容量上限，非長久之計）。
什麼情況該重新檢討：Storage 用量也開始逼近免費額度時，評估升級方案或
清理舊檔案。

**2026-09-16｜為什麼先做車輛維修（而非其他模組）**
決定：業務模組開發順序上，「車輛維修」是最早做完整（含照片、付款狀態、
自動加總）的模組之一。
理由：維修相關的支出與付款狀態是最容易「忘記追蹤」、也最常需要對帳的
項目，同時牽涉照片憑證需求，優先做完可以驗證「照片 + 金額 + 付款狀態」
這套共用模式，再套用到零用金、保險、對帳等其他模組。
其他選項：先做出車報班（業務量最大但邏輯較單純）。
什麼情況該重新檢討：不適用，這是開發順序的歷史決定，不影響現有功能。

**2026-09-16｜為什麼暫不用 n8n（或其他工作流自動化平台）**
決定：目前的通知/自動化都用前端輪詢（`js/notify.js`）+ Supabase trigger
（`notify_task_assignment`），沒有導入 n8n 之類的工作流平台。
理由：現有需求（工作單指派通知、Claude Code 回報）用資料庫 trigger 加
前端輪詢就能滿足，不需要額外維護一個工作流平台的部署與帳號。
其他選項：n8n（需要自架或另外付費託管，多一個系統要維護）。
什麼情況該重新檢討：出現需要串接多個外部服務、排程、或複雜條件分支的
自動化需求時（例如 LINE 推播、排程檢查到期項目），評估 Supabase Edge
Functions 或 n8n 哪個投入產出比較好。

**2026-09-16｜為什麼快速新增用一排按鈕而非自然語言輸入框**
決定：總覽頁「今天要記什麼？」用固定的一排膠囊按鈕（維修單/加油/出車
報班/零用金/發票/更多），不做自然語言輸入框去猜使用者要新增哪一種資料。
理由：目標使用者不一定習慣打字描述需求，且系統本身沒有 AI 判斷輸入
內容該對應哪個模組的邏輯；固定按鈕可預期、零學習成本、不會有辨識錯誤
導致資料填錯的風險。
其他選項：自然語言輸入框 + AI 判斷（需要額外呼叫 LLM API、增加不確定性
與延遲，且失敗時使用者不容易理解為什麼）。
什麼情況該重新檢討：如果使用者回饋普遍希望有更快的輸入方式，且能接受
AI 判斷偶爾出錯的風險時。

**2026-09-16｜為什麼不開 Dependabot、不強制 PR 流程**
決定：GitHub repo 維持現況——不開啟 Dependabot security updates，main 分支
不加分支保護規則，不強制走 PR 流程，維持可以直接 push 到 main。
理由：目前是單人（使用者＋Claude Code）維護，沒有其他協作者需要 code
review 這道關卡；前端沒有 `package.json`／固定相依套件版本，主要外部
依賴是 `index.html` 裡用 CDN 直接引入的 `xlsx`/`jszip`（版本寫死在
`<script>` 標籤網址上），Dependabot 主要抓的是 `package.json`／
lockfile 裡的套件漏洞，這個專案的形狀讓它幾乎沒有可以抓的目標；
強制 PR 流程會拖慢單人快速迭代任務包的節奏，且沒有第二個人要審查。
其他選項：開 Dependabot（等以後真的加了套件依賴時再評估）；加分支保護
強制 PR（等有其他協作者加入、或想留審查紀錄時再評估）。
什麼情況該重新檢討：專案開始有其他協作者加入、或前端開始用
`package.json`／npm 套件依賴管理時。
